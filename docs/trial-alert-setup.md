# Daily trial checks and email alerts

The code is implemented for both Alzheimer’s Access and Free the Burp. Pushing it does not activate email delivery. The database migration, an email provider and the daily workflow must be connected first. Until then, pages show the dated existing catalogs and explain that alerts are not available.

## One-time setup

1. **Database:** in the existing Supabase project’s SQL Editor, run `supabase/migrations/202610080001_trial_monitor.sql` once. It adds private tables and server-only functions; it does not modify the existing profile, trial or criteria tables. All new tables have row-level security and no anonymous/authenticated access. The script is a transaction. If it fails, resolve the error before continuing; do not rerun after a successful application.
2. **Email:** create a [Resend account](https://resend.com/docs/introduction), verify a domain you control using its [domain setup instructions](https://resend.com/docs/dashboard/domains/introduction), and create a sending API key. Disable open/click tracking for this sending domain so private management links are not rewritten for tracking. A `vercel.app` subdomain or Riteesha’s Gmail address cannot be used as your own verified sending domain. Use an address on the verified domain as `TRIAL_ALERT_FROM`. Replies go to `riteesha.lingechetty@gmail.com`. Check the provider’s current quota before inviting users; confirmation emails count too. No SMS provider is needed for this release.
3. **Vercel production environment:** keep the existing Supabase URL and service-role key. Add `RESEND_API_KEY`, `TRIAL_ALERT_FROM`, `TRIAL_ALERT_SITE_URL=https://alzheimers-access.vercel.app`, and `TRIAL_ALERT_SECRET` (a new random secret of at least 32 characters). Initially set `TRIAL_ALERTS_ENABLED=false`. Never put secrets in a `NEXT_PUBLIC_` variable, Git, screenshots or chat. Keep the site URL and secret configured even when pausing delivery so users can still manage/delete subscriptions. Redeploy after changing Vercel variables.
4. **GitHub Actions:** under repository Settings → Secrets and variables → Actions, add secrets `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `TRIAL_ALERT_SECRET`. Use the same values as Vercel. Add repository variables `TRIAL_ALERT_SITE_URL`, `TRIAL_ALERT_FROM`, `TRIAL_ALERTS_ENABLED=false` and `TRIAL_MONITOR_ENABLED=true`. This needs repository settings permission. Riteesha may need to do this if you lack it.
5. **Baseline:** in Actions → Daily trial checks → Run workflow, leave “Publish…” off to audit. After it succeeds, run again with “Publish…” on. The first complete run establishes a baseline and sends no change alerts. Check both sites show the new “Last complete registry check” date. A run that is skipped means the `TRIAL_MONITOR_ENABLED` repository variable is missing/false.
6. **Enable and verify:** set `TRIAL_ALERTS_ENABLED=true` in both Vercel and GitHub variables, redeploy, then sign up with an inbox you control. Confirm using the button on the linked page, follow a study, save preferences, and verify deletion using a disposable test subscription. Check Resend’s delivery log for the confirmation email. Real email delivery and the production database have not been tested from this local development session. The local PostgreSQL tests exercise the migration and consent/deletion logic without patient data.

Generate a secret locally (do not paste its output into chat):

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

## What runs daily

The GitHub workflow runs at **11:23 UTC** (07:23 Eastern daylight time, 06:23 Eastern standard time). [GitHub schedules can be delayed](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); the sites warn when the last complete check is over 48 hours old. No Vercel paid cron plan is needed. Private repositories use the account’s Actions allowance. Keep GitHub workflow-failure notifications enabled for the operator.

Each run fetches every ClinicalTrials.gov result page for the dementia search and all five Free the Burp conditions. Previously open and followed studies missing from search results are fetched directly to establish their actual status. A failed page, inconsistent count, invalid ID or missing direct lookup prevents publication; absence alone never means “closed.” Publication switches an atomic database pointer only after the complete snapshot and alert queue are ready. The sites read that snapshot without another Git commit or deployment.

New matching alerts require a recruiting, explicitly relevant listing and a transition into the user’s broad preferences. Age, country/state, site recruitment, travel preference and any unchanged previously parsed study-partner criteria are checked. Missing details remain uncertain. Condition stage, biomarkers, genetics and the rest of clinical eligibility are not assessed. New/changed eligibility text invalidates previous parsed criteria rather than trusting an old interpretation. The site continues to call these potential leads, never eligibility decisions.

Explicit follows trigger recruitment-status, eligibility/age-limit, site or study-contact changes regardless of matching preferences. A new subscriber or newly followed study starts from a baseline. Users receive one email per daily check with meaningful changes; no routine weekly digest and no email when nothing changed. Users can follow up to 50 studies per site and change their preferences through a private email link. Management credentials stay in URL fragments, are signed with the server secret, and are not included in ordinary HTTP URLs or referrers. Email confirmation links are single-use and expire after 24 hours; opening one does not activate a subscription until the user presses Confirm.

## Operation and recovery

- Local read-only registry check: `npm run trials:registry-check`. This uses public records only; no database, patient data or email.
- Database-aware audit: `npm run trials:monitor`. It reads the current snapshot/subscriptions and prints aggregate counts; no writes or email.
- Publish/send: `npm run trials:monitor:apply`. This is a production mutation when production environment variables are loaded. Prefer the serialized GitHub workflow. Do not run simultaneous local workers.
- Email is sent through the [Resend API](https://resend.com/docs/api-reference/emails/send-email). Queue records and [provider idempotency keys](https://resend.com/changelog/idempotency-keys) prevent ordinary retries from producing duplicates. A send lease prevents concurrent claiming. The provider retains idempotency keys for 24 hours: after 22 hours, an unconfirmed send is marked `uncertain` and requires operator review rather than blindly risking another email.
- If a run reports an unconfirmed send, inspect the Resend log using the `trial-update/<outbox UUID>` idempotency key and recipient. Retry the workflow after the ten-minute lease expires and within 22 hours for a safe automatic retry. After that, confirm in Resend whether it was accepted; mark it `sent` if accepted, or deliberately requeue only after establishing it was not sent. Never reset uncertain rows wholesale. Quota errors, bounces and provider failures need operator attention. `sent` means accepted by the provider, not guaranteed inbox delivery.
- If delivery is paused, set `TRIAL_ALERTS_ENABLED=false` in both places; keep the daily registry workflow running and keep the management secret/site URL. Existing subscriptions can still be deleted. No new email backlog is created while delivery is disabled; resuming watches for future changes. Unsent queued alerts older than 48 hours are cancelled, rather than sending outdated changes. For a full monitor pause, also set `TRIAL_MONITOR_ENABLED=false`; freshness warnings will appear after 48 hours.
- Expired confirmation requests and hashed rate-limit counters are deleted after successful runs. Only the latest two full registry payload snapshots are kept. Sent/cancelled alert history is cleaned after 90 days. Preference changes reset the baseline and cancel pending old-preference messages. Subscription deletion cascades to queued/history rows and removes pending confirmation requests for that site. Provider logs/backups follow their separate policies.
- Rotating `TRIAL_ALERT_SECRET` revokes existing management links. Users can confirm their email again to obtain a new link. Do not reuse this secret elsewhere.

## Validation performed locally

Production build and lint; automated tests for matching, meaningful changes, first-run baselines, pagination, missing-record direct checks, source-change invalidation, signed links, disabled email and provider idempotency. An isolated PostgreSQL runtime executes the actual SQL migration and tests confirmation, permissions, atomic publication, send leases, late retry protection, unfollow and cascading deletion. No real patient records were created/deleted and no actual emails were sent.

Public API smoke check on 8 October 2026: 1,529 records retrieved with reconciled page counts; 1,320 explicit inclusions, 141 requiring relevance review, and 33 included Free the Burp studies. These numbers can change on later runs. The check does not assert patient eligibility or individual-site availability.
